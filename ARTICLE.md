# The rewrite that looked fine

A reviewer approves a pull request that changes one SQL query. The diff is three lines: a `LEFT JOIN` becomes a plain `JOIN`, because someone noticed the query was slow and figured an inner join would let the planner do less work. It compiles. It runs. On the reviewer's laptop, against a small sample of production data pulled for testing, it returns the same numbers it always did. It ships.

Three weeks later, finance asks why net revenue for a specific cohort of orders quietly dropped by four percent. Nobody touched the revenue logic. Eventually someone finds the join. Every order that never got a matching row in the discounts table, previously included with a zero discount via the left join, is now silently gone. The query did not break. It just started answering a slightly different question, and nothing about running it told anyone that had happened.

This is not a hypothetical, it is the most common failure mode in SQL-heavy data engineering, and it has a specific and unglamorous reason it keeps happening: a SQL query is a sentence in a language where small grammatical changes can produce large semantic ones, and the usual tools for catching that, code review and a handful of fixture-based unit tests, are both bad at it for the same root cause. A human reviewer reads a diff and asks "does this look reasonable," not "does this produce the same output on the edge cases that matter," because nobody has the patience to mentally execute a three-table join across a thousand hypothetical rows. A fixture test checks the query against the same five rows every time, which means it only ever tests the inputs someone already thought of.

## Borrowing a fifty-year-old idea from software testing

The software testing literature solved an adjacent problem decades ago, for ordinary code rather than SQL: if you cannot prove two programs are equivalent, generate a lot of random inputs, run both programs, and see if they agree. This is differential testing, and its honest selling point has always been a disclaimer, not a guarantee: agreement across many random trials is evidence, not proof. The interesting engineering work is entirely in understanding and reporting exactly how much evidence, which depends on whether the random inputs you generate actually visit the inputs where the two programs could disagree.

That is also where mutation testing comes in, as the method for measuring how good the "random inputs" part actually is. You take a program known to be correct, introduce a small, realistic, deliberate bug (a mutant), and check whether your testing approach notices. The fraction of mutants your tests catch is the mutation kill rate, and a low kill rate is a direct, falsifiable signal that your tests are not doing what you think they are doing, independent of how many of them pass.

sql-equivalence-guard applies both ideas to one narrow, concrete problem: given a reference SQL query and a candidate rewrite of it, generate many realistic synthetic datasets, run both queries against the same data in DuckDB, and compare. Then, instead of stopping there, build a small corpus of hand-written, realistic mutants, exactly the kind of change a real reviewer would wave through, and measure the kill rate honestly, including the cases where it is bad.

## Building the corpus, and finding the first bug in the project's own logic

The corpus is five base queries drawn from ordinary data-pipeline work: a daily-active-users rollup, a revenue aggregation with a discount join, a top-incident-per-day ranking, an SLA compliance threshold, and an average with NULL handling. Each gets a hand-written mutant (drop the DISTINCT, narrow the join, flip the ORDER BY direction, tighten the boundary, remove the COALESCE) and, to measure false positives, a hand-written safe rewrite that is syntactically different but should compute the same answer.

Early on, comparing the reference and candidate queries for the ranking case produced a false positive: a RANK()-based rewrite, reasoned to be exactly equivalent to a ROW_NUMBER()-based reference, was reported as a behavior change. The actual bug turned out to be in the oracle itself, not the SQL: the code that decided whether row order mattered for comparison was matching the literal substring "order by" anywhere in the query, including inside a window function's `OVER (... ORDER BY ...)` clause, which has nothing to do with the final row order of the query's output. That flipped the comparison from an order-insensitive multiset check to a strict list comparison, and DuckDB does not guarantee row-fetch order without a genuine top-level ORDER BY. The fix is a parenthesis-depth-aware scan that only counts an ORDER BY sitting outside every set of parentheses. It is now a regression test in the suite, because the failure mode (a correct safe rewrite reported as risky, for a reason that has nothing to do with the SQL in question) is exactly the kind of false alarm that erodes trust in a tool like this fastest.

## The result that was not supposed to happen

With that bug fixed, the RANK()-versus-ROW_NUMBER() pair genuinely came back equivalent, on ordinary random data. But the project's data generator has a second feature, built for an unrelated reason: a tunable bias toward "interesting" values, including occasionally injecting an exact duplicate row, to model something that really happens in production pipelines, an upstream retry or a message replayed twice. Turn that bias on, and the RANK pair starts disagreeing, often: roughly three-quarters of the time at a moderate bias setting, across 500 trials.

The reason is almost embarrassingly simple once you see it. `ROW_NUMBER()` assigns strictly increasing numbers even to rows that tie on every column in the ORDER BY; among two byte-identical duplicate rows, exactly one gets rank 1. `RANK()` assigns the same rank to genuine ties, so both duplicate rows get rank 1, and a filter on `rn = 1` now returns two rows where it used to return one. The original reasoning, "the tiebreaker column makes the sort key unique, so RANK and ROW_NUMBER must agree," is correct for every case except exact full-row duplicates, which it silently assumed away. Nobody designed this into the corpus as a mutant. It was a wrong assumption in the project's own test design, caught by the same machinery being built to catch other people's wrong assumptions, which is as good an argument for building something like this as any benchmark number could be.

## What the honest numbers actually say

The full sweep is reproducible with one script and lives in `eval/results.json`. The two numbers that matter most: at zero edge-case bias, a dropped `COALESCE` is caught 0% of the time across 500 trials, and a narrowed SLA boundary (`<=30` tightened to `<30`) is caught only 5.8% of the time, because landing on an exact threshold value by uniform chance is rare. Turn a modest bias on, and both climb to 100%, while the four genuinely safe rewrites in the corpus stay at a strict 0% false-positive rate across 6,000 trials. Neither number is cherry-picked, and the first one is the actual point: a differential-testing tool with no opinion about what data is interesting is a weak safety net for precisely the bugs, NULL handling and boundary conditions, that matter most in a billing or SLA calculation.

That is the shape of the claim this project is willing to make: not "this proves your rewrite is safe," but "here is exactly how much testing pressure it takes to catch what, measured honestly, including the week it caught a bug in its own test corpus instead of someone else's."
